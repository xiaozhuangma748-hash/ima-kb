## 九、新发现的问题

### 9.1 B2"殡葬服务流程"BM25 Top1 退步（b 参数调优副作用）

- **现象**：
  - 改进前 BM25 Top1：钱塘区实施方案（骨灰寄存服务流程），score=8.61，⚠️ 部分相关
  - 改进后 BM25 Top1：白事服务热线战略发展思考（提前登记奖励），score=8.31，⚠️ 部分相关
  - 改进后 #2 才是钱塘区，score=8.17（与 #1 仅差 0.14）
- **根因**（已通过对比 `b=0.5` vs `b=0.35` 验证）：

  ```
  b=0.5（旧）: #1 钱塘区 8.64 / #2 白事服务热线 8.04  →  Top1 正确
  b=0.35（新）: #1 白事服务热线 8.31 / #2 钱塘区 8.17  →  Top1 退步
  ```

  - b 减小 → 文档长度归一化减弱 → 长文档（"白事服务热线战略发展思考"）不再被长度惩罚
  - 钱塘区 chunk 含骨灰寄存服务流程原文，相对较长；"白事服务热线"chunk 也较长但 token 命中分布不同
  - b=0.35 让"白事服务热线"分数上升 0.27，钱塘区下降 0.47，导致反转
- **影响**：B2 改进前已是"部分相关"，改进后仍是"部分相关"，**严格意义上不算回归**，只是 Top1 文档换了。但 #2 仍是钱塘区，整体可接受
- **Hybrid 也未修复**：B2 被分类为 `normal`（不含疑问词），权重 1:1，向量 boost 不足
- **建议缓解**：
  1. 在 `_PRECISE_MARKERS` 增加"流程"，让 B2 走 precise 路径（bm25=0.7），强化 BM25 主导
  2. 或在 `_classify_query` 中增加规则：含"服务+流程/办理/政策"组合时走 precise
  3. 或对 `_rerank_by_exact_match` 扩展：当查询含多字 token（如"殡葬""服务""流程"）时，对 chunk content 同时包含全部多字 token 的结果加权
  4. 短期可接受现状——B2 在改进前后都是部分相关，没有真正回归

### 9.2 H-B4 出现 source=vector 单独主导（改进 3 副作用，可观察）

- **现象**：H-B4 在 fuzzy 权重（vector=0.7）下，Top1 是 `source=vector`（紫阳街道海潮社区），BM25 候选未进入
- **对比**：改进前 H-B4（1:1 权重）Top1 是 `source=both`（闸弄口街道天运社区）
- **评估**：两个结果都命中 xlsx 智能服务终端配置表，**功能上正确**，只是具体社区不同
- **可观察点**：vector=0.7 权重下，BM25 候选可能被完全压制，丢失"精确匹配重排序"的好处（如 H-A1 中 _rerank_by_exact_match 让晨光社区从同街道多个社区中脱颖而出的机制）
- **建议**：在 `_rrf_fusion` 中对 BM25 Top1 添加最低保留分（如 `bm25_results[:3]` 强制进入融合），避免完全被向量主导

### 9.3 D1"养老服务"仍单文档偏置（与改进前一致）

- **现象**：D1 Top10 全部来自 xlsx 单文档
- **根因**：xlsx 中 75 个 chunks 都含"养老服务"，BM25 自然把它们排满
- **影响**：未变化，建议引入查询改写或文档类型多样性约束（原报告建议 5）

## 十、改进建议（基于复测结果）

### 建议 A：扩展 _PRECISE_MARKERS，覆盖"服务流程/办理/政策"等组合词（**中优先级**）

**依据**：B2"殡葬服务流程"被分类为 normal，未能触发 precise 路径的 BM25 主导，导致 Top1 退步。

**具体动作**：在 `core/retrieval/hybrid.py` 的 `_PRECISE_MARKERS` 增加：
```python
_PRECISE_MARKERS = (
    "街道", "社区", "镇", "村", "区", "市", "省",
    "号", "字", "〔", "【", "第",
    "照料中心", "服务中心", "服务站", "管理站",
    # 新增：政务文档常见组合词
    "服务流程", "办理流程", "实施方案", "政策",
)
```

### 建议 B：在 Weighted RRF 中对 BM25 Top 候选设最低保留分（**低优先级**）

**依据**：H-B4 出现 `source=vector` 单独主导，BM25 候选完全被压制，丢失 `_rerank_by_exact_match` 的精确匹配重排序机制。

**具体动作**：在 `_rrf_fusion` 中，对 BM25 Top3 的 chunk 强制赋最低 RRF 分数（如 `max(scores[cid], w_bm25 * 1.0 / (RRF_K + 3))`），保证 BM25 精确匹配的优势结果不丢失。

### 建议 C：B2 的根因 — b 参数调优需配合查询类型（**低优先级**）

**依据**：b=0.35 解决了 C3 短文档虚高问题，但引入了 B2 长文档抬升问题。单一 b 值无法同时优化两类场景。

**具体动作**：可考虑在 `BM25Index.search` 中按查询长度动态调整 b：
- 短查询（< 5 token）：用 b=0.35（避免短文档虚高）
- 长查询（>= 5 token）：用 b=0.5（避免长文档抬升）
- 但这会增加复杂度，建议先用建议 A 解决 B2

### 建议 D：D1 单文档偏置仍存在（**低优先级**）

与原报告建议一致，建议引入文档类型多样性约束或查询改写。
