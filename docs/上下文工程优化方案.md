# 上下文工程优化方案

> **版本**：v1.0
> **日期**：2026-07-28
> **范围**：core/qa/chain.py、core/pet/administrator.py、core/persona/prompts.py、core/retrieval/*、core/memory/*、config.py
> **目标**：提升 RAG 生成侧的上下文工程成熟度，从当前 2.9/5 提升到 4.0/5

---

## 一、现状评估

### 1.1 成熟度矩阵

| 维度 | 评分 | 关键短板 |
|---|---|---|---|
| 上下文组装 | 3/5 | 双体系割裂：chain.py 不带 history/记忆，administrator.py 走富上下文 |
| 上下文压缩 | 3/5 | 仅"前半+...+后半"硬截断，无语义压缩；PetAdministrator 路径未接入 |
| 多轮历史管理 | 4/5 | 有滑动窗口+滚动摘要，但字数代理 token，chain.py 生成阶段失忆 |
| Query 变换 | 4/5 | HyDE + 子问题分解工程化好，但 PetAdministrator 未接入 |
| Few-shot | 1/5 | 几乎完全缺失，零示例库，零动态召回 |
| Prompt 模板管理 | 2/5 | 硬编码字符串，无版本管理，无 A/B 测试 |
| Token 预算 | 1/5 | 零 token 计数，零预算分配，中文字数≠token |
| 记忆系统 | 3/5 | 三层记忆体系完善，但 chain.py 不用记忆，无衰减机制 |
| 引用溯源 | 4/5 | 完整注入-提取-验证链路，但重排后语义错位 |
| 格式感知 | 4/5 | 双层格式感知，但 persona 路径丢失格式提示 |

**加权平均：2.9/5** — 检索侧工程化程度高，生成侧上下文工程是明显短板。

### 1.2 三大结构性问题

#### 问题 1：双体系割裂

```
CLI/Web 主问答（chain.py）          桌面宠物（administrator.py）
┌─────────────────────┐            ┌─────────────────────────┐
│ system: 硬编码 prompt │            │ system: persona 模板     │
│ user:   检索资料+问题  │            │ system: 跨会话记忆       │
│                     │            │ system: 对话摘要         │
│ ❌ 无 history        │            │ history: 最近 10 条      │
│ ❌ 无 cross_session  │            │ user:   问题             │
│ ❌ 无 summary        │            │ ✅ 完整富上下文           │
└─────────────────────┘            └─────────────────────────┘
```

- `chain.py` 行 393-400：仅 `[system, user]` 两条消息
- `administrator.py` 行 247-253：5 段消息（system + cross_session + summary + history + user）

#### 问题 2：零 Token 预算

- 全局无 tiktoken，用 `max_chars` 字数代理 token
- 中文 1 字 ≈ 1.5-2 token，`context_max_chars=800` 实际约 1200-1600 token
- 长对话 + parent_content 扩展后，input 可能超过模型窗口直接报错

#### 问题 3：Few-shot 完全缺失

- 核心 RAG system prompt（chain.py 行 63-73）零示例
- LLM 对"如何标注 [n]"、"何时声明资料不足"的理解全靠规则文字
- 需要靠 `sanitize_outbound_citations` 兜底清理越界引用

## 二、市面成熟方案对比

### 2.1 Anthropic Context Engineering（最权威）

**核心观点**：上下文工程是 prompt 工程的自然演进，关注"什么样的上下文配置最可能产生期望的模型行为"。

**关键概念**：
- **Context Rot**（上下文腐烂）：随着上下文长度增加，模型召回关键信息能力显著下降
- **黄金信噪比法则**：用最少 token 承载最大信息量
- **动态剪枝策略**：实时淘汰低价值信息
- **Goldilocks Zone**：指令既要足够具体又要有灵活性
- **四层架构**：系统提示 + 工具设计 + Few-shot + 子智能体

**适用性**：★★★★★ — 直接对应项目的 system prompt / 工具 / few-shot / 多轮对话

### 2.2 LLMLingua / LLMLingua-2（微软）

**核心能力**：粗到细的 prompt 压缩，含 Budget Controller + 迭代 token 级压缩。

**关键特性**：
- 基于困惑度（perplexity）的 token 重要性评估
- 预算控制器在高压缩率下保持语义完整性
- 2x-10x 压缩比，保持任务性能

**适用性**：★★★☆☆ — 项目 context_max_chars=800 过于粗暴，但 LLMLingua 引入重依赖，**可借鉴思路用 LLM 摘要式压缩替代字符截断**

### 2.3 LangChain LCEL + Memory

**核心组件**：
- `ConversationTokenBufferMemory`：按 token 数（非轮数）管理历史
- `ConversationSummaryMemory`：滚动摘要
- `ManagedMemory`：多类型记忆统一管理
- LCEL 表达式语言：`prompt | model | parser` 可组合管道

**适用性**：★★★☆☆ — 项目已有等价实现（滑动窗口+摘要），但 **token 计数**和**记忆类型分层**值得借鉴

### 2.4 Loop Engineering（2025 新范式）

**核心观点**：从"手动 prompt"到"设计自动 prompt 的循环"。

**四层架构**：
- 智能体循环（执行任务）
- 验证循环（质检）
- 事件驱动循环（自动触发）
- 爬坡循环（自我优化）

**适用性**：★★☆☆☆ — 项目暂不需要 agent 循环，但**验证循环**（引用验证、事实核查）可加强

### 2.5 LlamaIndex Context

**核心能力**：节点级元数据管理、上下文窗口优化、Sentence Window Retrieval。

**适用性**：★★★☆☆ — 项目的 Parent-Document Retrieval 已等价于 Sentence Window，但**元数据驱动的上下文裁剪**值得借鉴

## 三、优化方案（按 ROI 排序）

### P0-1：统一上下文组装路径

**问题**：chain.py 只有 `[system, user]`，CLI 主问答多轮失忆。

**方案**：让 chain.py 的 `ask()` / `ask_stream()` 也接受 `history`、`cross_session_context`、`summary` 参数，组装方式对齐 administrator.py。

**改动点**：

1. `core/qa/chain.py` 的 `ask()` 和 `ask_stream()` 方法签名增加参数：
   ```python
   def ask(
       self,
       question: str,
       top_k: Optional[int] = None,
       history: Optional[List[dict]] = None,          # 新增
       enable_hyde: bool = True,
       enable_decompose: bool = True,
       doc_ids: Optional[List[str]] = None,
       cross_session_context: Optional[str] = None,    # 新增
       summary: Optional[str] = None,                  # 新增
   ) -> Answer:
   ```

2. 消息组装改为（对齐 administrator.py 行 247-253）：
   ```python
   messages = [{"role": "system", "content": SYSTEM_PROMPT}]
   if cross_session_context:
       messages.append({"role": "system", "content": f"## 跨会话记忆\n{cross_session_context}"})
   if summary:
       messages.append({"role": "system", "content": f"## 之前的对话摘要\n{summary}"})
   if history:
       messages.extend(history[-10:])  # 最近 10 条
   messages.append({"role": "user", "content": user_prompt})
   ```

3. `services/qa_service.py` 传入 history/summary/cross_session_context

4. 统一 `_history_augmented_query` 逻辑（chain.py 与 administrator.py 目前重复且不一致）

**验证**：
- 单元测试：`test_chain_ask_with_history` / `test_chain_ask_with_cross_session`
- 回归测试：现有 244 个测试全通过

### P0-2：引入 Token 预算系统

**问题**：零 token 计数，中文字数严重低估实际消耗。

**方案**：引入 tiktoken，实现 `TokenBudget` 分配器。

**新增文件**：`core/context/token_budget.py`

```python
"""
Token 预算分配器。

按模型窗口大小分配 token 预算：
- system_prompt:   固定 800 token
- retrieval_context: 动态，按相关性分配（默认 2000）
- history:          动态，滚动截断（默认 800）
- user_query:       保留 200
- margin:           安全边距 296
- total:            4096（可配置）

超预算时自动截断，优先保留：
1. system prompt（不动）
2. user query（不动）
3. retrieval context（按分数排序保留 top-N）
4. history（从最早开始截断）
"""
```

**改动点**：

1. 新增 `core/context/__init__.py` 和 `core/context/token_budget.py`
2. `core/context/token_budget.py` 实现：
   - `count_tokens(text: str) -> int`：用 tiktoken 计数
   - `TokenBudget` 类：预算分配 + 超预算截断
   - 支持 `model_name` 参数（不同模型 tokenizer 不同）
3. `chain.py` 和 `administrator.py` 构造 prompt 前调用预算器
4. `config.py` 增加 `token_budget` 配置项
5. 替换所有 `max_chars` 为 `max_tokens`：
   - `context_max_chars=800` → `context_max_tokens=2000`
   - `summary_max_chars=500` → `summary_max_tokens=800`
   - `_history_augmented_query` 每条 120 字 → 200 token

**验证**：
- 单元测试：`test_token_budget_allocation` / `test_token_budget_truncate`
- 端到端：长对话场景下 token 计数准确

### P2-2：记忆系统统一与衰减

**问题**：ProfileManager 和 CrossSessionMemory 的 topics 重叠；无衰减机制。

**方案**：

1. **统一来源**：合并 topics/regions 到 ProfileManager（作为权威源），CrossSessionMemory 只存 preferences/questions/facts
2. **时间衰减**：引入 `weight = exp(-days / half_life)`，半衰期 30 天
3. **get_context() 按 weight 排序取 top-N**

**改动点**：

1. `core/memory/cross_session.py` 的 `get_context()` 增加衰减排序：
   ```python
   import math
   from datetime import datetime, timedelta

   def _decay_weight(timestamp: str, half_life_days: int = 30) -> float:
       """时间衰减权重，半衰期 30 天。"""
       try:
           ts = datetime.fromisoformat(timestamp)
           days = (datetime.now() - ts).days
           return math.exp(-days / half_life_days)
       except Exception:
           return 1.0
   ```

2. `CrossSessionMemory.get_context()` 按 weight 排序，取 top-N（默认 5 条/类）
3. `ProfileManager.focus_topics` 与 `CrossSessionMemory.topics` 合并，ProfileManager 为权威源
4. `_KNOWN_REGIONS` 从硬编码改为可配置（config.py）

**验证**：
- 单元测试：`test_memory_decay` / `test_memory_unified_topics`
- 回归测试：记忆相关测试全通过

### P3：引用溯源细粒度化

**问题**：重排后 [1] 不再是最相关的；无段落级溯源。

**方案**：

1. **重排后编号处理**：
   - 选项 A：重排后重新分配编号（[1] 永远是最相关的）
   - 选项 B：固定编号但提示用户"编号已按相关性重排"
   - **推荐选项 A**，更符合用户直觉

2. **段落级溯源**：
   - `chain.py` 的 `_build_user_prompt` 暴露 `paragraph_num`：
     ```
     [1] 来源：节地生态安葬奖补通知（第 3 段）
         内容：...
     ```
   - 支持 `[1§3]` 形式的段落级引用（LLM 生成，citation.py 解析）

**改动点**：

1. `chain.py._build_user_prompt()` 行 124-127 增加 paragraph_num 显示
2. `reorder_lost_in_middle()` 后重新分配编号
3. `citation.py` 解析 `[n§m]` 格式
4. `citation_validator.py` 验证段落号合法性

**验证**：
- 单元测试：`test_citation_paragraph_level` / `test_citation_rerank_renumber`
- 端到端：检索结果重排后引用编号正确

## 四、实施路线图

```
Phase 1（P0，2个任务）: 统一上下文组装 + Token 预算
  ├─ 1.1 chain.py 接入 history/summary/cross_session
  ├─ 1.2 引入 tiktoken，实现 TokenBudget
  ├─ 1.3 替换 max_chars 为 max_tokens
  └─ 1.4 全量回归测试（244+ 测试通过）

Phase 2（P1，2个任务）: 动态 Few-shot + 双路径压缩
  ├─ 2.1 建立示例库 + 动态召回
  ├─ 2.2 administrator.py 接入 compress + reorder
  ├─ 2.3 persona 模板接入 _FORMAT_HINTS
  └─ 2.4 评测对比（golden_dataset 100 题）

Phase 3（P2，2个任务）: Prompt 版本化 + 记忆衰减
  ├─ 3.1 prompt 迁移到 YAML + 版本注册表
  ├─ 3.2 记忆衰减 + ProfileManager 统一
  └─ 3.3 全量回归测试

Phase 4（P3，1个任务）: 引用细粒度化
  ├─ 4.1 paragraph_num 暴露 + 重排后编号处理
  ├─ 4.2 [n§m] 段落级引用解析
  └─ 4.3 端到端验证
```

### 预期收益

| 阶段 | 任务 | 成熟度提升 | 风险 |
|---|---|---|---|
| Phase 1 | 统一组装 + Token 预算 | 2.9 → 3.4 | 低（改动集中在 chain.py） |
| Phase 2 | Few-shot + 双路径压缩 | 3.4 → 3.8 | 中（示例库质量影响效果） |
| Phase 3 | Prompt 版本化 + 记忆衰减 | 3.8 → 4.0 | 中（迁移工作量大） |
| Phase 4 | 引用细粒度化 | 4.0 → 4.2 | 低（增量改进） |
