# 搜索准确率测试报告

> **测试时间**：2026-07-28
> **测试对象**：拱墅区"身后事"知识库（33 文档 / 341 chunks / 71,248 tokens）
> **测试范围**：BM25 检索 + BM25+向量 RRF 混合检索
> **测试方法**：`python -c` 临时脚本，未修改任何源码
> **环境**：`.venv` 虚拟环境 + `HF_ENDPOINT=https://hf-mirror.com`，bge-small-zh-v1.5 本地已下载

## 一、总体准确率统计

| 测试类别 | 查询数 | Top1 命中数 | 命中率 | 备注 |
|---|---|---|---|---|
| **A. 精确查询**（BM25） | 5 | 5 | **100%** | 全部命中预期目标 |
| **B. 模糊/口语化查询**（BM25） | 5 | 3 | **60%** | B1/B4 严重误命中 |
| **C. 边界场景**（BM25） | 5 | 5 | **100%** | 单字/错别字/停用词均正确处理 |
| **D. 跨文档查询**（BM25） | 2 | 2 | **100%** | D2 跨 5 个文档，D1 跨 5 个街道 |
| **混合检索对照**（Hybrid） | 6 | 6 | **100%** | 修复了 BM25 在 B1/B4 的所有误命中 |

**关键结论**：
- BM25 在 **精确/边界/跨文档** 场景表现优秀（15/15 = 100%）
- BM25 在 **口语化/语义查询** 场景有明显短板（3/5 = 60%），原因是不懂同义/语义
- **混合检索（BM25+向量 RRF 融合）** 在所有测试中都给出了正确结果，是推荐方案
- 单次 BM25 检索延迟 < 50ms，混合检索首查 ~250ms（含 embedding 计算），命中缓存后 < 30ms

| B5 | 社区照料中心在哪 | 2025年智能服务终端配置安装情况 | 7.86 | ✅ 命中 |

### B1 详细分析（典型 BM25 短板）

```
#1 score=7.8286  截图_20260707_191934 (PDCA循环管理工作法)
    content: Management Rnowledge | 管理知识库 PDCA循环管理工作法...
#2 score=1.5880  2025年智能服务终端配置安装情况
    content: 四季青街道居家养老服务照料中心
#3 score=1.5788  2025年智能服务终端配置安装情况
    content: 清波街道清波门社区居家养老服务照料中心
```

**问题根因**：
- jieba 把"养老中心有哪些"切成 `养老 / 中心 / 有 / 哪些` 等通用 token
- "中心"作为单字 token 在 PDCA 截图 chunk 中出现 4 次（"知识中心/中心/管理中心"），词频累加后 BM25 分数被推高
- 而真正的"居家养老服务照料中心"xlsx 行 chunk 较短，"养老"虽然命中但 IDF 较低（在 75 个 chunk 中都出现）
- 加上"哪些/有"等无意义 token 的干扰，PDCA 截图意外成为 Top1

### B4 详细分析（最严重的语义缺失）

```
#1-#5 全部是"白事服务热线战略发展思考"
    content: 优先级/行动项、技术演进路线、白名单星级体系、智能调度、云缅怀数字纪念园
```

**问题根因**：
- 用户意图是"查智能服务终端的安装情况"（应在 xlsx 中）
- BM25 把"智能终端怎么安装"切成 `智能 / 终端 / 怎么 / 安装`
- xlsx chunk 的内容是"街道=XXX | 名称=XXX | 摄像头序列号=XXX"，**根本不含"安装"二字**（只有表头"安装情况"在文档元信息里）
- 反而"白事服务热线战略发展思考"中出现"智能化升级""智能知识库""智能调度"等含"智能"的 chunk，被误命中
- 这是典型的 **词频统计 vs 语义理解** 差距，BM25 无法理解"安装情况表"= 用户想问的"安装"

### C2 错别字鲁棒性分析（亮点）

查询"晨光社区居养服务"少了"家"字，Top1 仍正确命中"晨光社区居家养老服务照料中心"：

```
#1 score=23.9184  白杨街道晨光社区居家养老服务照料中心
#2 score= 4.3599  浙民事〔2025〕84号（"民政部门"误命中"民"）
```

**起作用的关键机制**：
- `tokenize()` 同时调用 `jieba.cut_for_search` + `jieba.cut(cut_all=True)`，全模式会把"居家养老"切成更细粒度，部分 token 与"居养"重合
- bigram `晨光_社区` 作为整体参与匹配，IDF 极高（只在该 chunk 连续出现），主导了最终分数
- 这印证了 `core/search/bm25.py` bigram 设计的正确性

### C3 长查询的"短文档偏好"现象

查询"白杨街道晨光社区...九堡街道九塘社区...四季青街道..."三个社区串在一起，Top1 不是查询里第一个出现的晨光社区，而是九塘社区：

```
#1 score=65.78  九堡街道九塘社区居家养老服务照料中心    （chunk 仅含名称一行，长度最短）
#2 score=39.91  白杨街道晨光社区居家养老服务照料中心     （chunk 含摄像头/账号等附加字段，长度较长）
#5 score=36.25  四季青街道居家养老服务照料中心
```

**原因**：BM25 公式中 `b=0.5` 的文档长度归一化项让短文档得分占优——九塘社区所在 chunk 内容极短（只有"序号=43 | 街道=九堡街道 | 名称=九堡街道九塘社区居家养老服务照料中心"一行），导致同样 token 命中数下分数虚高。

### C5 停用词过滤验证

"的骨灰寄存" 与 "骨灰寄存"（A4）的 Top5 结果**完全一致、score 完全相同**，证明 `"的"` 被正确过滤为停用词，未参与打分。

## 八、发现的问题汇总

### 8.1 BM25 在口语化查询上存在严重语义缺失（B1/B4）

- **现象**：B1"养老中心有哪些"误命中 PDCA 截图；B4"智能终端怎么安装"完全错过 xlsx 安装清单
- **根因**：BM25 是词频统计模型，无法理解"养老中心"= "居家养老服务照料中心"、"安装"= "配置安装情况表"
- **影响**：约 40% 的口语化查询会受影响

### 8.2 xlsx chunk 内容缺乏字段名上下文（B4 根因之一）

- **现象**：xlsx 解析后每个 chunk 只有"序号=XX | 街道=XX | 名称=XX | 摄像头序列号=XX"，不含表头"安装情况"
- **影响**：用户用"安装"作为查询词时，BM25 无法在 chunk 内容里命中"安装"二字，必须依赖文档标题
- **当前缓解**：`DocumentRecord.title` 会参与某些链路，但 BM25 索引只索引 chunk content

### 8.3 短文档在长查询中被 BM25 长度归一化虚高（C3）

- **现象**：长查询拼接 3 个社区名，Top1 是内容最短的九塘社区 chunk，而非查询里第一个出现的晨光社区
- **根因**：`b=0.5` 的文档长度归一化让短 chunk 在相同 token 命中数下得分虚高
- **影响**：用户输入"我想要 A、B、C 三个"时，返回顺序与输入顺序不一致（轻微问题）

### 8.4 通用词 token 干扰 Top1 排序（B1 根因之一）

- **现象**：B1 中"中心"作为单字 token 在 PDCA 截图出现 4 次，累加后超过真正的照料中心 chunk
- **根因**：单字 token "中心"未进入停用词表；`tokenize()` 的全模式切分放大了高频通用词的影响
- **缓解**：当前 IDF 公式 `max(0, ln((N-n+0.5)/(n+0.5)+1))` 已经把高频词的 IDF 截断到 0，但单字 token "中心"的文档频率没高到被截断

### 8.5 跨文档查询 D1 单文档偏置

- **现象**：D1"养老服务"Top10 全部来自 xlsx 单文档
- **根因**：xlsx 中 75 个 chunk 都含"养老服务"，BM25 自然把它们排满
- **影响**：用户可能想看其他文档（政策类）中的养老服务条款，但被清单类文档淹没

## 九、改进建议

### 建议 1：默认启用混合检索，BM25 仅作降级方案（**高优先级**）

**依据**：H-B1 和 H-B4 的对照测试证明，向量检索 + RRF 融合可在不改 BM25 任何代码的情况下修复全部口语化查询问题。当前 `HybridRetriever` 实现已经成熟，向量索引本地化已就绪。

**具体动作**：
- `services/qa_service.py` 等上层调用方默认走 `HybridRetriever.search`，仅在 `vector.is_available() == False` 时降级到 `bm25_search`
- 在 `config.py` 增加 `retrieval_mode` 配置项（`hybrid` / `bm25_only`），默认 `hybrid`

### 建议 2：xlsx 行 chunk 入库时拼接表头上下文（**高优先级**）

**依据**：B4 失败的核心是 xlsx chunk 内容不含"安装"字段名，导致任何包含"安装"的查询都命中不了。

**具体动作**：
- 在 `core/ingestion/chunker.py` 处理 xlsx 时，把 sheet 名 + 表头（如"安装情况 / 序号 / 街道 / 名称"）作为前缀注入到每个行 chunk 的 content 中
- 这样 chunk content 变为 `"[安装情况] 序号=6 | 街道=白杨街道 | 名称=..."`，BM25 即可命中"安装"
- 同样适用于 `政策汇集表.xlsx`（每个 sheet 名"六项免费政策"等是有价值的语义信息）

### 建议 3：扩充单字停用词，抑制通用词干扰（**中优先级**）

**依据**：B1 中"中心"作为单字 token 在管理类文档高频出现，挤掉了真正的"居家养老服务照料中心"。

**具体动作**：
- 在 `core/search/bm25.py` 的 `_STOP_WORDS` 增加：`中心 / 服务 / 工作 / 系统 / 平台 / 管理` 等单字通用词
- 注意：这些词作为单字 token 时无区分价值，但作为 bigram 一部分（如 `服务_流程`、`中心_安装`）应保留——当前 bigram 生成逻辑会过滤掉停用词，所以加了停用词后 bigram 也不会生成
- **更稳妥的做法**：不加入停用词，而是在 `_rerank_by_exact_match` 中对单字 token 的匹配率计算降权（如单字 match_ratio 权重 0.5，多字 token 权重 1.0）

### 建议 4：调低 BM25 的 b 参数或对短文档设最小长度（**低优先级**）

**依据**：C3 中九塘社区 chunk 因内容极短（只有名称一行）被 BM25 长度归一化推到 Top1，与用户长查询里的顺序不符。

**具体动作**：
- 当前 `b=0.5`，可尝试 `b=0.3`（业界中文常用 0.25~0.5），减少文档长度对分数的影响
- 或在 `BM25Index.search` 中对 `length < avgdl * 0.3` 的极短文档施加惩罚项
- 注意：调参会全局影响所有查询，需要用 A 部分精确查询回归验证不引入回归

### 建议 5：引入查询改写（Query Rewriting）前置步骤（**中优先级**）

**依据**：用户口语化查询（B1/B4）与文档原词差距大，单靠检索层无法完全弥合。

**具体动作**：
- 在 `core/retrieval/query_transform.py` 已有基础设施的基础上，加一个 LLM-based 查询改写步骤：
  - 输入："智能终端怎么安装"
  - LLM 改写为："智能服务终端 配置 安装情况 摄像头 健康一体机"
  - 再用改写后的 query 走 BM25/混合检索
- 成本控制：仅当 BM25 Top1 score < 阈值（如 5.0）或查询包含疑问词（"怎么/如何/哪些/在哪"）时触发
- 这能解决"养老中心有哪些"→"居家养老服务照料中心"、"怎么办理身后事"→"身后事一件事办理流程"等口语-书面语鸿沟

## 十一、测试结论

1. **BM25 在精确/边界/跨文档场景表现优秀**（15/15 = 100%），bigram + 全模式分词 + 精确匹配重排序三件套有效
2. **BM25 在口语化/语义查询场景有明显短板**（3/5 = 60%），B1/B4 暴露了词频统计模型的固有局限
3. **混合检索（BM25 + 向量 RRF）是当前最佳方案**，6/6 = 100% 命中，且修复了 BM25 的全部误命中案例
4. **建议生产环境默认启用混合检索**，并将 xlsx 表头注入 chunk content 作为入库侧改进
5. 短期内即可见效的优化顺序：**建议 2（xlsx 表头注入）→ 建议 1（默认混合检索）→ 建议 5（查询改写）→ 建议 3（停用词调优）→ 建议 4（参数调优）**
