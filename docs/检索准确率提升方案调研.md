# RAG 检索准确率提升方案调研

> **调研时间**：2026-07-28
> **调研范围**：2024-2026 年业界主流 RAG 检索优化技术
> **针对场景**：中文政务文档知识库（PDF / Word / Excel / 扫描件 OCR / PPT 混合）
> **项目现状基线**：33 文档 / 341 chunks / BM25+向量 RRF 混合检索 Top1 命中率 100%（精确+边界+跨文档）/ 60%（口语化）

## 一、优先级排序方案清单（按投入产出比）

### 方案 1：Excel / 表格表头上下文注入

- **核心思想**：在 xlsx 解析为行级 chunk 时，把 sheet 名 + 表头字段名作为前缀注入到每行 chunk 的 content 中，让 BM25 和向量都能命中字段名词。
- **适用场景**：直接解决 B4（"智能终端怎么安装"查不到 xlsx 清单）和 D1（清单类文档淹没政策文档）的根因——当前 chunk content 形如 `序号=6 | 街道=白杨街道 | 名称=...`，完全不含"安装""配置"等字段名，BM25 无法命中。
- **实施难度**：低
- **预期收益**：高
- **依赖**：无外部依赖，纯 chunker 改动
- **落地建议**：
  - 文件：`core/ingestion/chunker.py` 的 `_chunk_excel()` 函数
  - 改动点：在按行切分前，从 `ParsedDocument` 提取 sheet 名（已有 `[SheetName]` 前缀）和首行表头，构造前缀模板，如 `"[安装情况·字段:序号/街道/名称/摄像头序列号/健康一体机编号] "`
  - 前缀拼到每行 chunk content 开头；`parent_content` 保持整 sheet 合并不变
  - 注意：前缀要简短（控制在 60 字内），避免重复前缀稀释向量语义；建议只在每行 chunk 开头注入一次，不在 parent_content 中重复
  - 同步处理 `政策汇集表.xlsx`（每个 sheet 名如"六项免费政策"本身就是高价值语义信息）
  - 验证：用 B4 查询"智能终端怎么安装"回归，期望 Top1 命中 `2025年智能服务终端配置安装情况.xlsx`

### 方案 2：BGE-M3 三合一模型升级（Dense + Sparse + ColBERT）

- **核心思想**：用 `BAAI/bge-m3` 一次性替换 `bge-small-zh-v1.5`，单模型同时输出稠密向量、稀疏向量（learned sparse，类 SPLADE）、ColBERT 多向量三种表示。稠密做语义召回，稀疏做关键词精确匹配（替代 BM25 的部分短板），ColBERT 做 late-interaction 精排。
- **适用场景**：
  - 解决 B1/B4 口语化召回不足（稀疏头理解"养老中心"≈"居家养老服务照料中心"）
  - 解决 BM25 在同义词/口语词上的固有缺陷（learned sparse 比 jieba+TF-IDF 更懂语义）
  - 提升短文档场景的排序质量（ColBERT MaxSim 比 BM25 长度归一化更鲁棒）
- **实施难度**：中
- **预期收益**：高
- **依赖**：需下载 bge-m3 模型（约 2.3GB，比 bge-small-zh 大 4 倍）、sentence-transformers≥2.7、Milvus 或 ChromaDB 支持多向量（ChromaDB 需自建 sparse+colbert 索引层）
- **落地建议**：
  - 文件：`core/retrieval/vector.py` 的 `_MODEL_NAME` 和 `_get_embedding_function()`
  - 第一阶段（低风险）：仅替换 dense embedding 为 bge-m3，保持现有 BM25+向量 RRF 架构不变，回归 A/B/C/D 测试集确认无退化
  - 第二阶段：启用 bge-m3 的 sparse 输出，新增 `core/retrieval/sparse_vector.py`，作为第三路检索信号加入 `hybrid.py` 的 RRF 融合（三路：BM25 + Dense + Sparse）
  - 第三阶段（可选）：启用 ColBERT 多向量，作为 rerank 前的精排层（替代或补充 Cross-Encoder）
  - 注意：bge-m3 推理延迟比 bge-small-zh 高约 3 倍，需评估查询 P95 延迟；建议 embedding 缓存（已有 `_EmbeddingCache`）覆盖 query 端
  - 算力：CPU 可跑（batch=8 约 200ms/query），有 GPU 更佳
  - 模型路径：`storage/models/bge-m3/`，沿用现有 HF 镜像下载逻辑

### 方案 3：单字通用词降权 + BM25 参数调优

- **核心思想**：针对 B1（"中心"单字 token 在 PDCA 截图高频干扰）和 C3（短文档长度归一化虚高），通过停用词扩充、单字 token 降权、b 参数调优三管齐下。
- **适用场景**：
  - B1：单字 token "中心/服务/工作/系统/平台/管理" 在管理类文档高频出现，挤掉真正的目标 chunk
  - C3：九塘社区 chunk 内容极短，b=0.5 长度归一化让其分数虚高
- **实施难度**：低
- **预期收益**：中
- **依赖**：无
- **落地建议**：
  - 文件：`core/search/bm25.py`
  - 改动点 1（单字降权，比加停用词更稳妥）：在 `search()` 的 BM25 打分循环中，对 `len(qt) == 1` 的单字 token 施加 0.5 的 IDF 衰减系数（`idf *= 0.5 if len(qt) == 1 else 1.0`），保留其召回能力但降低排序权重。注意 bigram（如 `晨光_社区`）不受影响，因为 bigram 长度≥3
  - 改动点 2（b 参数）：`BM25Index.__init__` 的 `b` 默认值从 0.5 试调到 0.35（中文常用 0.25-0.5），减轻短文档优势。k1 保持 1.5
  - 改动点 3（极短文档惩罚，可选）：对 `entry.length < avgdl * 0.3` 的 chunk 在打分后乘 0.8 惩罚系数
  - **不要**把"中心/服务"加入 `_STOP_WORDS`——会破坏 bigram 生成（bigram 函数会过滤停用词）
  - 验证：用 A1-A5（精确查询）回归确保不引入退化；用 B1 验证 PDCA 截图是否跌出 Top1

### 方案 4：Weighted RRF / 查询自适应融合权重

- **核心思想**：当前 `hybrid.py` 用标准 RRF（两路权重各 1.0）。改为：根据查询类型动态调整 BM25 与向量的融合权重——口语化/模糊查询 boost 向量，精确/实体查询 boost BM25；并支持 RRF-Enhanced（在 RRF 分数上叠加原始归一化分数的 10-20% 加权）。
- **适用场景**：
  - B1/B4：口语化查询应让向量主导（向量已能修复 B1/B4，但 RRF 平权时优势被稀释）
  - A1-A5：精确实体查询应让 BM25 主导（BM25 在精确查询上 100% 命中）
  - D1：清单类查询可通过"文档级去重权重"避免 75 个 xlsx chunk 霸榜
- **实施难度**：中
- **预期收益**：中
- **依赖**：无
- **落地建议**：
  - 文件：`core/retrieval/hybrid.py` 的 `_rrf_fusion()`
  - 改动点 1（查询类型识别）：新增 `_classify_query(query) -> Literal["precise","colloquial","list"]`，基于启发式：含疑问词（怎么/如何/哪些/在哪/有哪些）→ colloquial；含具体实体（社区名/街道名/政策编号正则）→ precise；含"有哪些/清单/列表/全部"→ list
  - 改动点 2（动态权重）：RRF 公式改为 `score = w_bm25 * 1/(k+rank_bm25) + w_vec * 1/(k+rank_vec)`，其中 `precise: (0.7, 0.3)`，`colloquial: (0.3, 0.7)`，`list: (0.5, 0.5)`
  - 改动点 3（RRF-Enhanced，可选）：在 RRF 分数上叠加 `0.15 * normalized_original_score`，让原始分数差异也参与最终排序
  - 改动点 4（文档级去重，针对 D1）：在 `sorted_ids` 取 top_k 前，对同 doc_id 的结果限制最多 N 个（如 5），让出位置给其他文档
  - 验证：H-B1/H-B4 仍命中，A1-A5 不退化，D1 Top10 覆盖文档数从 1 提升到 ≥3

### 方案 5：Multi-Query Retrieval（多查询扩展）

- **核心思想**：让 LLM 对单个用户查询生成 N 个语义不同的改写变体，并行检索后合并去重，再走 rerank。区别于现有 HyDE（只生成 1 个假设答案）和子问题分解（拆成子问题），Multi-Query 是同一意图的多种表述扩展。
- **适用场景**：
  - B1："养老中心有哪些" → 扩展出"居家养老服务照料中心名单""社区养老机构清单""养老服务设施分布"等，提升召回覆盖率
  - B4："智能终端怎么安装" → 扩展出"智能服务终端配置情况""摄像头健康一体机安装清单"等，弥补 BM25 词汇鸿沟
  - 与 HyDE 互补：HyDE 生成"假设答案"（文档风格），Multi-Query 生成"多种问法"（查询风格），两者覆盖不同语义空间
- **实施难度**：低
- **预期收益**：中
- **依赖**：LLM 调用（已有 `LLMClient`）
- **落地建议**：
  - 文件：`core/retrieval/query_transform.py`，新增 `multi_query_expand()` 函数
  - 改动点：新增 `_MULTI_QUERY_PROMPT`，要求 LLM 输出 3-5 个改写查询（JSON 数组），温度 0.5 鼓励多样性
  - 触发条件：仅在 `len(query) >= 6` 且查询类型为 `colloquial`（与方案 4 联动）时触发，避免精确查询被过度改写
  - 集成点：`transform_query()` 返回的 `QueryTransformResult` 增加 `multi_queries: List[str]` 字段；`hybrid.py` 的 `search()` 对每个变体并行检索，合并 chunk_id 去重后取 top_k*2 候选送 rerank
  - 成本控制：每个变体复用同一 query embedding 缓存；最多 5 个变体；变体 query 长度限制 50 字
  - 与现有 HyDE 关系：Multi-Query 优先，若 Multi-Query 触发则跳过 HyDE（避免 LLM 调用叠加）

### 方案 6：Cohere Rerank 3.5 / Voyage AI 专用 Rerank API

- **核心思想**：用托管型专用 rerank API 替换当前的 LLM prompt 打分（`core/retrieval/rerank.py`）。Cohere Rerank 3.5 支持 100+ 语言、原生处理 JSON 和表格、单次最多 100 文档、延迟约 200ms；Voyage AI rerank-2 在多语言基准上表现更优。
- **适用场景**：
  - 当前 LLM Rerank 延迟 1-3s、成本高（每查询约 1000 tokens）、对长 chunk 有截断
  - Cross-Encoder（bge-reranker-v2-m3）已用但仅本地，无 GPU 时延迟较高
  - Cohere/Voyage 对表格类内容（xlsx 行 chunk）的语义理解优于 LLM prompt 打分
  - 解决 C3（短文档虚高）：rerank 不依赖文档长度，只看 query-doc 语义相关性
- **实施难度**：低
- **预期收益**：中
- **依赖**：Cohere API Key（付费，约 $2/1k 查询）或 Voyage API Key（约 $0.05/1k token）；需联网
- **落地建议**：
  - 文件：新增 `core/retrieval/hosted_rerank.py`，实现 `HostedReranker` 类，接口对齐 `CrossEncoderReranker.rerank()`
  - 集成点：`core/retrieval/rerank.py` 的 `create_reranker()` 工厂增加 `hosted_cohere` / `hosted_voyage` 选项，优先级：Cross-Encoder > Cohere/Voyage > LLM > None
  - 配置：`config.py` 增加 `cohere_api_key`、`voyage_api_key`、`reranker_type` 支持 `hosted_cohere`
  - 降级策略：API 超时/限流时自动降级到 Cross-Encoder 或 LLM Reranker（复用现有降级链）
  - 注意：政务场景需评估数据出境合规性——若不可出境，仅用本地 Cross-Encoder，跳过本方案
  - 中文表现：Cohere Rerank 3.5 在中文基准上表现优秀，Voyage rerank-2-lite 支持中文且更便宜

### 方案 7：Contextual Retrieval 结构感知优化（已有基础增强）

- **核心思想**：项目已实现 Contextual Retrieval（`core/ingestion/contextualizer.py`），但当前只用"文档标题 + 截断 2000 字全文"让 LLM 生成摘要。优化为：注入结构信号（sheet 名、slide 标题、章节标题层级），让摘要更精准；并增加摘要持久化缓存避免重建索引时重复调用 LLM。
- **适用场景**：
  - Excel chunk：当前摘要只看文档标题"2025年智能服务终端配置安装情况"，不知 chunk 属于哪个 sheet、哪一行；优化后摘要能说"本片段是上城区安装情况表中闸弄口街道天运社区的配置记录"
  - PPT chunk：当前不知 slide 标题；优化后能说"本片段是 PPT 第 5 页'技术演进路线'的内容"
  - 重建索引时避免重复 LLM 调用（当前每次重建都重新生成摘要，成本高）
- **实施难度**：中
- **预期收益**：中
- **依赖**：LLM 调用（已有）、SQLite（已有）
- **落地建议**：
  - 文件：`core/ingestion/contextualizer.py`
  - 改动点 1（结构信号注入）：`_USER_TEMPLATE` 增加结构字段：`{section_path}`（章节路径，如"上城安装情况 > 第 17 行"）、`{format_tag}` 已有但未充分利用；从 `ParsedDocument` 提取 chunk 所属 sheet/slide/heading
  - 改动点 2（摘要缓存）：新增 `core/ingestion/context_cache.py`，用 SQLite 存 `(chunk_content_hash, context_summary)` 映射；`contextualize_chunks()` 先查缓存命中则跳过 LLM 调用
  - 改动点 3（摘要质量校验）：增加摘要长度校验（50-150 字）、摘要与原 chunk 的实体重叠率校验（如要求摘要包含原 chunk 至少 1 个命名实体），不达标则重试 1 次
  - 改动点 4（成本控制）：对 Excel 行级 chunk 批量生成——同一 sheet 的所有行只调一次 LLM 生成 sheet 级摘要，每行 chunk 前缀 sheet 摘要 + 行级简述（节省 90% LLM 调用）
  - 验证：对比优化前后 B1/B4 的 Top1 命中情况；统计 LLM 调用次数下降比例

### 方案 8：GraphRAG / 图谱增强检索（已有 graph 模块激活）

- **核心思想**：项目已有 `core/graph/extractor.py` 和 `core/graph/store.py`，但图谱仅用于可视化，未参与检索。激活图谱增强检索：用 LLM 从文档中抽取实体（政策名、服务项、办理条件、责任部门）和关系，构建知识图谱；检索时先在图谱中找到 query 实体的邻居实体，把邻居实体的相关 chunk 加权加入候选。
- **适用场景**：
  - 政策文档间有大量交叉引用（如"浙民事〔2025〕84号"被各区实施方案引用），图谱能捕捉这种引用关系
  - 用户问"海葬和树葬的区别"时，图谱能定位"海葬"和"树葬"两个实体，召回两个实体各自的定义 chunk + 对比关系 chunk
  - 解决 D1 单文档偏置：图谱天然跨文档连接
- **实施难度**：高
- **预期收益**：中
- **依赖**：LLM 调用（已有）、图谱存储（已有 `core/graph/store.py`）、可选 NetworkX
- **落地建议**：
  - 文件：`core/graph/extractor.py`（增强抽取 schema）、`core/retrieval/graph_augment.py`（新增）
  - 改动点 1（schema 定义）：定义政务领域实体类型（Policy/Service/Department/Condition/Document）和关系类型（references/issued_by/applicable_to/contains）
  - 改动点 2（检索增强）：新增 `graph_augment_search(query, top_k)`，先用 NER/LLM 抽取 query 实体，在图谱中找 1-2 跳邻居实体，把邻居实体关联的 chunk_id 作为额外候选加入 RRF 融合（权重 0.3）
  - 改动点 3（混合策略）：图谱增强作为第四路检索信号加入 `hybrid.py`，与 BM25+Dense+Sparse 并行 RRF 融合
  - 注意：图谱构建成本高（每文档 1 次 LLM 调用），建议离线一次性构建；图谱质量依赖抽取 prompt，需迭代调优
  - 验证：用"海葬和树葬的区别及各自费用"类多实体查询测试图谱召回效果
  - 备选：评估 LightRAG（香港大学开源）作为更轻量的图谱 RAG 方案，比微软 GraphRAG 部署简单

### 方案 9：ColBERT Late-Interaction 精排

- **核心思想**：ColBERT 用延迟交互机制（MaxSim）替代双塔余弦相似度——query 和 doc 分别编码为 token 级向量序列，检索时对 query 每个 token 找 doc 中最相似的 token 向量求和。比双塔更准（token 级匹配），比 Cross-Encoder 更快（可预计算 doc 端）。
- **适用场景**：
  - 解决 B1（"中心"单字干扰）：ColBERT token 级匹配能让 query 中"养老"token 只与 doc 中"养老"token 计算相似度，不被无关"中心"token 干扰
  - 解决 C3（短文档虚高）：ColBERT 的 MaxSim 不依赖文档长度，只看 token 级最大相似度
  - 作为 rerank 层：在 BM25+向量 RRF 粗排后，用 ColBERT 对 top 20 精排
- **实施难度**：中
- **预期收益**：中
- **依赖**：Jina-ColBERT-v2（支持 89 语言含中文）或 BGE-M3 的 ColBERT 输出头（与方案 2 联动）
- **落地建议**：
  - 前置条件：建议与方案 2（BGE-M3）一起实施，复用 BGE-M3 的 ColBERT 输出，避免单独加载 ColBERT 模型
  - 文件：新增 `core/retrieval/colbert_rerank.py`
  - 改动点：实现 `ColBertReranker.rerank(query, candidates, top_n)`，用 BGE-M3 的 `colbert_vecs` 输出计算 query 与每个 candidate 的 MaxSim 分数
  - 集成点：`create_reranker()` 工厂增加 `colbert` 选项；优先级：ColBERT > Cross-Encoder > LLM（ColBERT 与 Cross-Encoder 功能重叠，二选一即可）
  - 注意：ColBERT 多向量存储成本高（每个 chunk 存 ~128 个 token 向量），341 chunks 可接受，大规模需用 PLAID 引擎优化
  - 备选：若不用 BGE-M3，可单独用 `jina-colbert-v2`（中文表现优秀，89 语言）

---

### 方案 10：嵌入模型微调（Fine-tune Embedding）

- **核心思想**：用领域 Q&A 对微调 bge-small-zh-v1.5 或 bge-m3，让 embedding 更懂政务殡葬领域术语（如"身后事一件事""节地生态安葬""骨灰寄存"等专有名词的语义）。
- **适用场景**：
  - 通用 embedding 模型对政务专有名词理解不足（如"身后事"在通用语料中少见）
  - 有明确的领域查询-文档正样本对时可显著提升召回
- **实施难度**：高
- **预期收益**：低
- **依赖**：训练数据（需标注 200+ query-doc 正样本对）、GPU（1 张 3090 即可）、`FlagEmbedding` 或 `sentence-transformers` 训练框架
- **落地建议**：
  - 数据准备：从 `tests/eval/golden_dataset.json` 和 `docs/搜索准确率测试报告.md` 的 A/B/C/D 测试用例整理训练集，人工标注 200-500 对 (query, positive_chunk, negative_chunks)
  - 训练框架：用 `FlagEmbedding` 的 `FineTune`（BAAI 官方），对比学习损失（InfoNCE），hard negative mining
  - 评估：用 `scripts/eval_retrieval.py` 的 golden dataset 做 before/after 对比，要求 MRR@10 提升 ≥5%
  - **不推荐近期实施**：当前知识库仅 341 chunks，通用 bge-m3 已能覆盖；微调收益有限且有过拟合风险。建议知识库扩展到 5000+ chunks 后再考虑
  - 替代方案：用 LLM 对政务术语生成同义词表，注入 BM25 的 `tokenize()` 做查询扩展（成本低 10 倍）

## 三、方案冲突与互斥分析

| 冲突方案对 | 冲突原因 | 处理建议 |
|---|---|---|
| **方案 6（Cohere Rerank） vs 方案 9（ColBERT）** | 两者都是精排层，功能重叠 | 二选一。ColBERT 本地免费但需算力；Cohere 托管省事但付费+数据出境 |
| **方案 5（Multi-Query） vs HyDE（已有）** | 都是 LLM 查询改写，叠加调用成本翻倍 | 互斥触发：Multi-Query 优先，触发后跳过 HyDE；或按查询类型分流 |
| **方案 2 的 Sparse 输出 vs BM25（已有）** | 都是稀疏检索，功能重叠 | 不冲突但需调权重。建议保留 BM25（精确查询强）+ BGE-M3 Sparse（同义词强），RRF 融合时 BM25 权重 0.6、Sparse 权重 0.4 |
| **方案 2 的 ColBERT 输出 vs Cross-Encoder（已有）** | 都是精排，功能重叠 | 二选一。BGE-M3 ColBERT 复用 embedding 模型更省内存；Cross-Encoder 独立模型更准。建议 BGE-M3 ColBERT 优先（省一次模型加载） |
| **方案 10（微调） vs 方案 2（BGE-M3 升级）** | 升级基础模型后微调需重做 | 先升级 BGE-M3 稳定 1-2 月后再考虑微调，避免重复劳动 |
| **Self-RAG / FLARE 动态检索 vs 当前"始终检索"** | Self-RAG 让 LLM 自行决定是否检索，与当前 RAG 架构冲突 | **不推荐引入**。小知识库（341 chunks）始终检索成本可接受，Self-RAG 的训练/推理复杂度过高，收益不匹配 |
| **方案 8（GraphRAG）的 LLM 抽取 vs 方案 7（Contextual）的 LLM 摘要** | 都在入库阶段调用 LLM，成本叠加 | 分时执行：Contextual 在首次入库时完成；GraphRAG 抽取作为离线批处理任务，不影响入库延迟 |

## 四、中文场景特殊注意点

### 4.1 分词（jieba）注意点

- **当前实现已较优**：`core/search/bm25.py` 的 `tokenize()` 同时用 `cut_for_search` + `cut_all=True` + bigram，覆盖率好
- **可优化项**：
  - 加载政务领域自定义词典：`jieba.load_userdict()`，加入"身后事""节地生态安葬""骨灰寄存""居家养老服务照料中心"等未登录词，避免被切散
  - 自定义词典文件：`storage/dict/political_terms.txt`，格式 `词 词频 词性`（如 `身后事 100 n`）
  - 注意：加载自定义词典后需重建 BM25 索引（已有 `bm25_index_path` 持久化机制）
- **避免的坑**：
  - 不要用 `jieba.posseg.cut` 做 BM25 分词（词性标注慢 3 倍，且对检索无增益）
  - 不要对单字 token 全部过滤（如"骨""灰"单字无意义，但"费""税"单字有意义）

### 4.2 中文 Embedding 模型选择

| 模型 | 维度 | 中文表现 | 推理速度 | 推荐度 |
|---|---|---|---|---|
| bge-small-zh-v1.5（当前） | 512 | 中（MTEB-zh 63.5） | 快（CPU 50ms） | 当前够用 |
| bge-large-zh-v1.5 | 1024 | 中上（MTEB-zh 64.8） | 慢（CPU 200ms） | 不推荐，性价比低 |
| **bge-m3** | 1024 | 优（MTEB-zh 66+，多语言） | 中（CPU 150ms） | **强烈推荐**（方案 2） |
| jina-embeddings-v3-zh | 1024 | 优 | 中 | 备选（API 付费） |
| text-embedding-3-large（OpenAI） | 3072 | 优 | 快（API） | 不推荐（数据出境+付费） |
| Conan-embedding-v1（腾讯） | 768 | 优（MTEB-zh 70+） | 中 | 备选（中文 SOTA） |

- **关键建议**：升级优先选 bge-m3，理由：开源免费、三合一输出、中文表现优秀、与现有 bge-reranker-v2-m3 同源兼容
- **不要**用支持中文但非中文原生的模型（如 OpenAI text-embedding-3、Voyage-2）做主 embedding——中文政务术语理解不如国产模型

### 4.3 中文 Reranker 选择

- **当前 bge-reranker-v2-m3 已是中文 SOTA 之一**，无需更换
- 若需托管 API：Cohere Rerank 3.5 中文表现优秀（方案 6）
- Voyage rerank-2 中文支持但非专精，不推荐优于 bge-reranker-v2-m3
- **不要**用 LLM prompt 打分做主 reranker（当前 `rerank.py` 的 LLM 路径仅应作降级）——延迟高、成本高、对长 chunk 截断

### 4.4 中文 BM25 参数经验值

- `k1`：1.2-2.0（当前 1.5，合理）
- `b`：0.25-0.5（当前 0.5，偏高；中文短文档多建议 0.3-0.4）
- IDF 公式：当前 `max(0, ln((N-n+0.5)/(n+0.5)+1))` 已截断负 IDF，正确
- **中文特有坑**：单字 token 的文档频率计算需谨慎——"的"在几乎所有文档出现（IDF→0，正确），但"费"在 30% 文档出现（IDF 未被截断，可能干扰）。方案 3 的单字降权可缓解

### 4.5 政务文档特殊处理

- **政策编号**：如"浙民事〔2025〕84号"应作为整体 token，加入 jieba 自定义词典
- **日期格式**：中文日期"2025年7月28日"应避免被切散，建议在 `tokenize()` 前用正则替换为 ISO 格式"2025-07-28"
- **OCR 乱码**：扫描件 OCR 可能有错字，BM25 容错差；建议 OCR 后用 LLM 做一次"文本净化"（纠错+补标点），已超出本调研范围

## 八、结论

1. **项目已具备较强的 RAG 基础设施**（混合检索+HyDE+Cross-Encoder+Contextual Retrieval+Parent-Document），主要短板在数据侧（Excel 表头缺失）和参数侧（单字干扰、b 偏高）
2. **最高 ROI 的三件事**：方案 1（表头注入）+ 方案 3（单字降权）+ 方案 4（Weighted RRF），2-3 人日即可解决测试报告中的全部已知问题
3. **中期跃升靠模型升级**：方案 2（BGE-M3）是能力分水岭，建议第 4 周启动
4. **避免过度工程**：方案 10（微调）和 Self-RAG 对当前规模不匹配，暂不引入
5. **中文场景核心**：jieba 自定义词典 + bge-m3 + bge-reranker-v2-m3 三件套是中文政务 RAG 的最佳本地化组合
